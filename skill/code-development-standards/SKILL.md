# 代码开发规范

## 适用场景

当用户要求编写代码、修改代码、重构、排查线上问题、补充测试或实现网关/服务/控制器逻辑时，遵循本规范。

## 注释要求

- 对外暴露的方法、接口方法、复杂私有方法，需要写必要的中文方法注释，说明用途、关键参数和返回含义。
- 关键业务分支、非显而易见的边界处理、协议/网关/第三方依赖的特殊行为，需要写简短中文行内注释。
- 不写机械注释，例如“设置变量”“调用方法”这类不能增加理解的信息。
- 注释要解释“为什么这样做”或“这里保护什么边界”，不要重复代码本身。

## 日志要求

- 外部调用、网关连接、第三方接口、批处理分页、文件上传、状态变更等关键路径，需要写中文日志。
- 日志应包含定位问题所需的关键字段，例如目标地址、业务ID、分页参数、耗时、结果行数、脱敏后的配置。
- token、密码、密钥、证书、cookie、手机号等敏感信息必须脱敏后输出。
- 异常日志需要包含业务上下文和根因摘要；需要保留异常对象，方便堆栈排查。

## Git 使用约定

- 当任务需要执行 Git 提交、变基、推送或其他 Git 写操作时，默认使用 Git 用户名 `Adong`，邮箱 `jhdong8855@gmail.com`。
- Git commit message 必须使用中文，不使用英文提交信息。

## 代码落点与简化原则

- 改问题前先追调用链、数据来源和影响范围，再决定落点。
- 问题在哪里产生，就优先在哪里修；不要把局部业务问题下沉到通用工具、基础库或框架层。
- 配置、校验、业务编排、外部调用、数据持久化各放各的位置，避免一个模块承担多种职责。
- 简单逻辑保持直接表达，不为了“看起来规范”增加包装类、包装函数、中间对象或多层转发。
- 抽象必须带来明确收益：减少真实重复、隔离变化、降低调用方理解成本；否则不要加。
- 修 bug 时先做最小范围修复，再考虑重构；不要借修 bug 顺手改无关结构。
- 改通用代码前，先确认所有调用方是否都适用新行为。
- 日志、注释、配置兜底要服务排障和理解，不要为形式而写。

## 实现偏好

- Controller 只做参数校验、协议转换和入口日志；业务编排放 domain service；外部连接放 gateway/infra。
- 大结果集读取必须考虑分页、流式处理或返回行数上限，避免一次性读全量数据到内存。
- 配置优先使用项目既有配置体系和 `@ConfigurationProperties`，测试中才允许手动加载配置文件做轻量验证。
- 新增配置项要给默认值或明确校验失败信息，避免线上启动后才出现难定位的空配置问题。
- DUCC 等配置中心的配置名统一使用小写字母加下划线格式，例如 `download_domain_mapping`，避免使用驼峰或大小写混排。

## 文档产出规范

- 产出产品文档、技术方案、任务计划、发现记录、进度记录等 Markdown 文件时，文件名优先使用中文，例如 `产品文档.md`、`技术方案.md`、`任务计划.md`、`发现与决策.md`、`进度日志.md`。
