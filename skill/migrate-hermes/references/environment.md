# 环境修复的判断依据

- **版本和 PATH**：对比旧机最后正常时间与新机实际安装版本，检查 CLI、浏览器扩展、Node/Python 和启动方式。按原始错误搜对应项目 issue、PR 和 release，再判断平台差异。不要默认安装最新版，更不要先修改商店扩展或第三方代码。
- **解释器**：shell 的 python3 与 Hermes 管理的解释器可能不同。在实际调用环境中检查 sys.executable 和所需模块；不把包装进另一个环境，也不任意替换管理中的解释器。
- **凭证**：配置被复制不代表 OS keychain、浏览器登录或 OAuth 会话可用。检查身份、scope 和资源授权；某次 API 需要 user 身份不能泛化成所有 bot 都只有只读权限。重新登录需用服务自身的授权流程，不输出 token。
- **平台路径**：先做路径清单，再对有效配置/脚本字段逐项映射。Windows 字体用可用字体候选探测替代写死路径；历史消息不批量替换。Windows/MSYS 特定的经验保留平台限定，不复制到 macOS 通用流程。
- **配置体积**：重写 YAML 可能去掉默认值或注释。比较生效语义，不能只按文件大小判断配置丢失。保留原件再修正。
- **残留与权限**：旧 exe/cmd/vbs/ps1、导入中间文件和锁文件先确认用途与占用状态，再隔离。WAL 可能含最新数据，不能按“残留”直接删除。凭据文件可修正访问权限，但不打印其内容。
- **业务链路**：按用户实际需要检查“读取资料→生成产物→后续动作”。环境恢复不自动授予发送、发布或激活定时任务的权限；缺授权的对外步骤可以先准备可审查的本地结果。
